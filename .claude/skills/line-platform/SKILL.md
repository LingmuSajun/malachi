LINE Messaging API、LIFF、料金体系、配信制限などプラットフォーム特性の参照知識。

- LINE Bot の機能設計時

- ユーザーへのメッセージ配信戦略を考える時

## LINE Messaging API の基本

### メッセージタイプ

| タイプ           | 用途               | Malachi での使用               |
| ---------------- | ------------------ | ------------------------------ |
| Text             | テキスト           | マラキの応答(主)               |
| Sticker          | スタンプ           | 通常使わない(世界観に合わない) |
| Image            | 画像               | カード画像送信                 |
| Video / Audio    | 動画・音声         | 使わない                       |
| Location         | 位置情報           | 使わない                       |
| Imagemap         | クリッカブル画像   | リッチメニュー代替             |
| Template         | ボタン・カード     | 簡易UIに使用                   |
| **Flex Message** | カスタムレイアウト | **メイン UI(カード引き等)**    |

### Flex Message

LINE 内で最もリッチな表現。
JSON ベースでレイアウトを記述する。

メリット:

- ボタン、画像、テキストの自由な配置
- LINE アプリ内で完結(LIFF 不要)
- ユーザー側のインストール負担なし

制限:

- 画像は HTTPS 経由のホスト必要
- JSON のサイズ制限あり(50KB)
- アニメーションはできない

### LIFF (LINE Front-end Framework)

LINE 内の WebView。LINE 認証情報を取得して、
リッチな UI(アニメーション、カードめくり、3D表現)を実装可能。

メリット:

- フル HTML/CSS/JS が使える
- LINE ユーザー ID を即時取得できる
- カード引きアニメ、占い結果のリッチ表示が可能

デメリット:

- 別途ホスティング(Vercel など)が必要
- 起動に若干のラグ
- LINE のWebView挙動の制約

### Malachi での使い分け方針

```
通常の鑑定: LINE Flex Message のみで完結
  ↓
カード選択: ボタンタップで実装

プレミアム鑑定 / 重要決断時: LIFF を起動
  ↓
カードめくりアニメ、複数枚スプレッドの可視化
```

## 料金構造(2025年時点の概算)

LINE 公式アカウントは料金プランがある:

| プラン                   | 月額     | 無料配信数  | 追加配信単価 |
| ------------------------ | -------- | ----------- | ------------ |
| コミュニケーションプラン | 0円      | 200通/月    | 不可         |
| ライトプラン             | 5,000円  | 5,000通/月  | 不可         |
| スタンダードプラン       | 15,000円 | 30,000通/月 | ~3円/通      |

※ 数値は時期により変動。必ず公式で再確認。

### 重要: 「配信」とは

- **応答メッセージ**(ユーザーの発言への返信): 配信数にカウントされない
- **プッシュメッセージ**(こちらから一方的に送る): 配信数にカウント

つまり:

- ユーザーが質問 → マラキが応答 → 無料
- 「今日の運勢を毎朝配信」 → 全ユーザーへの配信、コスト発生

### Malachi のコスト戦略

1. **応答中心の設計** — ユーザーが話しかけた時のみ反応 = 配信数 0
2. **プッシュは厳選** — 課金リマインドや特別な日(誕生日)のみ
3. **「今日の運勢」は LIFF で表示** — メッセージ配信ではなく、ユーザーがLIFFを開くと表示する設計に

これで配信コストをほぼゼロに抑えられる。

## ユーザー識別

LINE Messaging API では `userId`(LINE 内部 ID、文字列、約33文字)が払い出される。
このIDは:

- LINE 公式アカウントごとに異なる(チャネル単位)
- 同じユーザーでも別アカウントでは別 ID
- ユーザーの本名・電話番号は取得不可(プライバシー保護)
- アイコン・表示名は取得可能(ユーザー同意あれば)

Supabase の `users` テーブルでは `line_user_id` をユニークキーにする想定。

## 友だち追加と離脱

- 友だち追加: 即座に Webhook で通知される(`follow` イベント)
- ブロック: `unfollow` イベント
- ブロックされたユーザーへは送信不可(エラーになる)

CRM 設計では「ブロック率」を必ず追跡する。

## 規約・コンテンツ制限

LINE 公式アカウントには審査・運用ルールがある:

### 禁止コンテンツ

- アダルト・出会い系
- 違法サービス
- 過度な勧誘・スパム
- ユーザーの同意なき広告メッセージ

### 占いコンテンツの注意

- **悪質な占い**(不安を煽る、高額課金へ誘導)はアカウント停止リスクあり
- 透明な料金体系・解約条件の明示が必須

定期的に LINE の最新ガイドラインを確認すること。

## 開発環境

### Webhook の受信

- HTTPS 必須
- 署名検証必須(`x-line-signature` ヘッダー)
- 数秒以内の応答が望ましい(タイムアウトは数十秒だが、UX 上短く)

### Next.js (App Router) での実装パターン

```typescript
// app/api/line/webhook/route.ts
export async function POST(req: Request) {
  // 1. 署名検証
  const signature = req.headers.get('x-line-signature')
  const body = await req.text()
  if (!verifySignature(body, signature)) {
    return new Response('Invalid signature', { status: 401 })
  }

  // 2. パース
  const events = JSON.parse(body).events

  return new Response('OK', { status: 200 })
}
```
